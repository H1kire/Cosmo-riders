# Rust and WebAssembly

## Build

The workspace is rooted at `Cargo.toml`; `cosmo-core` builds as both `rlib` and `cdylib`. The browser package is generated by `wasm-pack` with target `web` into `src/wasm/pkg`. Generated glue and WASM files are build artifacts and are not hand-maintained.

## Worker boundaries

Two independent workers own different workloads:

- `src/rendering/geodesic/surface-tile-worker.ts` initializes WASM and generates surface channels, geodesic meshes and stitch indices. The bounded surface pool retains its existing queue and transfer behavior.
- `src/wasm/physics/physics-worker.ts` owns exactly one `PhysicsWorldHandle`. It serializes commands and snapshots for the application; the main thread does not run orbital propagation or vessel integration.

The physics worker is deliberately separate from surface generation. It does not require SharedArrayBuffer, atomics or WASM threads. Worker results use transferable typed-array buffers. A failed command is rejected through the bridge and is not silently rerun synchronously.

## Rust physics core

`crates/cosmo-core/src/physics_world.rs` owns the simulation state:

- ordered celestial-body hierarchy and unique identifiers;
- J2000.0 initial relative states and ephemeris propagation;
- parent-equator to inertial-frame conversion;
- fixed-step accumulator, time scale, pause and substep limit;
- arbitrary-time body snapshots without mutating committed simulation time;
- vessel relative state and patched-conics primary-body transitions;
- SOI enter/exit hysteresis and primary transition history;
- impulsive maneuvers and idealized rocket-equation burns as separate legacy/planning operations;
- multiple per-vessel engines with independent propellant, throttle, enable state, ISP and inertial thrust direction;
- RK4 continuous-thrust integration of vessel position, velocity and changing mass, including gravity, commanded burn-end events and engine-specific fuel-depletion events;
- current propulsion telemetry (resultant thrust, mass flow, acceleration and remaining propellant);
- analytic body spin metadata, Rust-computed spin phase at arbitrary render time and tidal-lock period derivation;
- optional barycentric N-body mode using pairwise Newtonian gravity and kick-drift-kick velocity Verlet; massless vessels are integrated as test particles in the combined field, while SOI remains presentation/primary metadata.

The catalog remains declared once in `src/physics/solar-system.ts`. `createSolarSystemBodyCatalog()` maps it into the WASM DTO once during worker initialization. The Rust engine does not contain a second hand-maintained planet catalog.

## WASM API

The existing numerical and surface exports remain available:

- `propagate_kepler`, `state_to_orbital_elements`, `orbital_elements_to_state`, `conic_elements_to_state`;
- `generate_surface_tile`, `build_geodesic_tile_mesh`, `build_geodesic_stitch_indices`;
- `gravitational_acceleration`, `specific_orbital_energy`.

The physics handle API is exported from `wasm_physics.rs`:

- `create_physics_world`, `add_celestial_body`, `initialize_ephemerides`;
- `enable_n_body`, `is_n_body_enabled` (opt-in; no UI selector or lossless reverse switch yet);
- `add_vessel`, `set_time_scale`, `set_paused`;
- `advance_simulation`, `step_simulation`;
- `get_body_states`, `get_body_states_at`, `get_vessel_state`, `get_vessel_state_at`;
- `get_sphere_of_influence`, `apply_maneuver`, `apply_idealized_burn`;
- `add_engine`, `start_engine_burn`, `set_engine_enabled`, `set_engine_throttle`, `set_engine_direction`, `get_propulsion_state`;
- `get_physics_snapshot`, `get_orbit_path`, `dispose_physics_world`.

Additional orbital computations are also available through the worker: state-to-elements, general conic elements-to-state conversion, orbital path sampling, orbital period, Hohmann transfer and plane-change delta-v. `PhysicsBridge.enableNBody()` and `PhysicsWorldClient.enableNBody()` select the dynamic mode in the same Rust-owned PhysicsWorld; it is not a second world.

Snapshots contain stable body and vessel ID tables plus packed `Float64Array` buffers. Each body occupies six values (position xyz, velocity xyz); a parallel rotation-angle array carries analytic spin phase (NaN denotes no independent spin, such as a tidally locked body); each vessel occupies thirteen values (position, velocity, relative position, relative velocity, mass). Primary-body IDs and transition metadata are carried alongside the packed numerical data.

## Application integration

`PhysicsWorldClient` is a DTO/cache adapter over `PhysicsBridge`; it does not integrate motion. The laboratory creates one client and one worker, loads the canonical catalog, adds its vessel, and renders committed/interpolated snapshots through the existing `Solar3DView` and WebGL2 path. The worker computes the interpolated body and vessel states for the frame. It precomputes each body's 1024-segment orbit path; Solar3DView samples that transferred path at its adaptive visual segment count rather than running TypeScript Kepler conversion.

`CelestialBody` instances remain as presentation metadata (names, radii, pole parameters, surface data and orbit descriptors). They are not an active simulation world. The legacy TypeScript `PhysicsWorld` remains available as a comparison reference while parity coverage is expanded.

## Verification

GitHub Actions builds the Rust/WASM package before the TypeScript quality audit. Automated coverage includes:

- all 50 catalog bodies at J2000.0, one day, 30 days and one year compared against the retained TypeScript reference using absolute and scale-relative tolerances;
- non-mutating arbitrary-time snapshots;
- elliptic, parabolic and hyperbolic conic conversion; universal-propagation reversibility;
- vessel-step and powered-burn parity against the TypeScript reference;
- powered-burn mass/fuel change, Hohmann transfer and orbital-period exports;
- Rust-generated orbit path closure and Solar3DView integration;
- SOI entry and preservation of absolute vessel position and velocity during primary-body switching;
- fixed-step pause/time-scale and max-substep accumulator behavior;
- N-body pair-force momentum conservation, bounded one-orbit energy error, reversibility, collision rejection, barycentric Sun motion and vessel-relative-state continuity across the frame transform.

The N-body mode uses a fixed outer simulation interval with adaptive step-doubling error control (one KDK step versus two half steps) inside each interval. This is not IAS15 and does not regularize singular close encounters. DE440/Horizons initial states, J2/relativistic corrections and dynamically sampled N-body orbit trails are not implemented yet. Continuous-thrust spacecraft use RK4 against the massive-body snapshot at the end of the current step; planetary N-body integration remains velocity-Verlet. Engine mount positions do not yet drive attitude or torque. These are automated tests, not a real browser/WebGL visual test. Runtime behavior on the user's GPU and visual orientation/seam quality still require a real application run.
